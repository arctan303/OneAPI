# 计划阶段契约

## 输入与选择

目标、范围、验收有可追溯依据；产品变更修订需求，维护可以使用维护契约。用户要求阶段计划或存在多个依赖里程碑时生成 Phase；其他情况复用短任务。

## 输出

- `docs/DEV-PLAN.md` 或现有等价索引：当前工作、必要下一步、依赖/阻塞摘要、明细与历史链接。
- `docs/dev-plan/phase-NN.md` 或原有明细：稳定 ID、目标、范围/非目标、任务与产物、验收、具体风险与证据。
- `depends_on` 写前置 ID 及实际需要的成果，无前置明确写无；`supersedes` 仅在有证据的替代时填写。文件搬迁不重编号。
- 实施、验证、审查、发布状态按需分开，不把已发布但审查证据缺口一律写成实施阻塞。

## 范围对账与维护

既有声明仍有效则保留，被承接则修订当前正文并标替代关系。用户已明确变更时直接补记录；不能只因为没有变更 ID 退回访谈。

已完成实施明细保留当时证据，可补后续替代元数据；未开始计划可以更新。多轮验证内容过长时独立文件并互链，不以摘要替代完整证据。详见[共同契约](../../../../.creator/references/workflow-contract.md)。

## 验收

下一会话可以定位当前阶段、所需前置成果和验证入口；未知不被写成事实。依赖应存在且无环，引用有效，活跃计划不与当前需求冲突。需要 Phase 时实际有文件，单一小改不机械扩成多阶段。

## Examples

先建立缓存再实现离线编辑、最后冲突同步：三个阶段以具体前置成果衔接。

已有权限下增加一个已确认导出选项：需求原位更新加短任务即可；不因为产品变更创建 R2 Phase。
