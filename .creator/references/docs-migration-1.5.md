# Creator 1.5 旧 docs 迁移手册

用途：把旧项目文档整理成可持续维护的当前知识、活跃计划与历史证据。供用户审阅，也供 Agent 在授权后执行。适用单体计划、分散 Phase、混合版本和自定义文件名；不操作业务代码、数据库、线上或其他仓库。

## 1. 范围与准备

工作流安装与 docs 迁移分开报告。用户要求“升级工作流并适配旧 docs”即可在该范围连续执行；只安装提示词时先只读盘点，不擅自迁移。只读约束优先。

1. 定位真实仓库，检查项目指令和未提交修改。正在被其他任务编辑的文档记录为待处理，不覆盖；其余独立迁移。
2. 检查 `.version`、manifest 和实际指令。日期形式的旧 `.version` 不能猜成语义版本，记未知/旧值；安装版本以释放包为准。
3. 找到已有入口；`project_spec.md`、`MANUAL.md`、`DESIGN.md`、`PROJECT-CONTEXT.md` 都可能有效，文件名不是判定依据。
4. 用现有 Git 差异/恢复方式保留可审阅基线，不自动提交、搭建回放引擎或重复备份树。没有可恢复基线时，先保留原文，再改当前入口，不能覆盖唯一证据。

只读盘点：`python .creator/scripts/check_docs.py --root .`。该工具输出 JSON，检查 Markdown 路径/大小/文件链接和迁移状态，不搬文件，不判断哪条产品决定正确。体积超建议只是提示。

## 2. 映射职责

复用等价文件，不强制改名或建空模板。默认名称只用于没有对应文件的项目。

| 职责 | 默认/可复用位置 | 内容 |
| --- | --- | --- |
| 当前入口 | `docs/README.md` 或现有总手册 | 能力、架构概览、当前里程碑、运行入口、限制、导航 |
| 有效需求/设计 | 现有 Spec / Design Brief | 预期行为、验收、当前约束，明确待实现 |
| 长期专题 | 现有 architecture/、MANUAL 或按需建立 | 模块职责、接口/数据边界、启动/构建/测试及依据 |
| 当前计划 | 现有 DEV-PLAN | 活跃/必要后续任务与历史导航 |
| 阶段/短任务 | 现有明细或 `docs/dev-plan/`、`docs/tasks/` | 承接关系、范围、任务、验收、状态和证据 |
| 历史 | 现有 archive 或按里程碑建立 | 完整旧任务、已替代决定、原始验证；不是当前约束 |

对本次纳入的每个文件记录：源路径、处置（保留/更新/拆分/合并/归档/待处理）、目标路径、理由。未识别的用户文档保留；未被引用不等于废弃。

## 3. 对账有效性

- 当前有效决定保留范围和来源；被替代的条款修订当前正文，历史标新决定/变更链接。
- 按明确替代证据判断，不能只按日期或代码现状。需求与实现冲突先判断待实现、回归、批准变更或记录滞后。
- “暂不做”注明基线/重审条件；已承接的限制撤销，仍成立的约束保留。
- 缺形式变更记录时根据已有确认补写。只有无法消解且会改变预期的冲突才问最多 2 个关键问题；其余独立工作继续。
- 缺失历史任务或审查证据记未知，禁止补造。仅有本地测试不能写已部署。

## 4. 拆分与承接

单体计划按原 Phase 边界迁出完整段落，保留 ID、任务、REQ/AC、命令、失败/跳过及证据。索引留活跃摘要和链接；旧锚点仍被引用时更新调用方，或留下指向新位置的兼容导航。

已拆分计划核对真实 `depends_on`（前置 ID + 所需成果）和有依据的 `supersedes`；不能把编号相邻当依赖。历史不重写，只补失效/承接元数据；未来任务可正常调整。

宽表中的过程移到相应明细；大 Phase 的多轮证据可另存并互链。当前规范提炼有效内容，完整原文可归档，不能用摘要替代唯一明细。

入口变大时按职责/模块拆专题，不按对话日期切碎当前知识。大小、长行和重复内容一起检查；详见[共同契约](workflow-contract.md)。

旧 `batch.md` 单独核对：有有效复查结论的条目按[共同契约](workflow-contract.md)保留必要回执/唯一明细后移出；未审、无法确认、问题未解决或证据已失效的项保留，不能因记录老或文件大就清空。全部关闭才重置为“当前无待复查项”，不把已复查历史搬回活跃队列。只读或并行编辑中的样本不执行清理。

## 5. 对齐状态

分别核对实施、验证、审查和发布。例如 `实施完成 / 验证通过 / 审查例外 / 已发布`，关联原有例外授权与发布证据。

历史 R2 不因新分级改写成“当时已通过”，也不无条件重审全部历史。相关证据缺口单独追踪；真正阻止当前目标的条件才标整体阻塞。

## 6. 迁移状态与恢复

`.creator/docs-state.json` 是一份轻量运行时记录；升级时保留，发布包不携带已完成模板。以下为格式示意，实际路径必须存在，没有的入口省略：

```json
{
  "schema_version": 1,
  "docs_schema_version": 1,
  "workflow_version": "1.5.0",
  "status": "partial",
  "entrypoints": {"context": "docs/README.md", "plan": "docs/DEV-PLAN.md"},
  "mappings": [
    {"source": "docs/DEV-PLAN.md", "action": "split", "targets": ["docs/DEV-PLAN.md", "docs/dev-plan/phase-01.md"], "reason": "原阶段全文和证据迁出，索引保留导航"}
  ],
  "pending": ["正在编辑的设计文档待对账"],
  "verified_at": "2026-09-06",
  "evidence": ["实际执行的检查与语义核对结果"]
}
```

status 为 `pending / partial / complete`；缺失表示未登记。action 为 `keep / update / split / merge / archive / pending`。待处理映射可以 targets 为空并写原因；source 可指搬迁前路径，targets/entrypoints 必须指向仓库内现存文件。

workflow_version 是本次适配依据，不替代 `.version`。docs_schema_version 表示文档协议。部分迁移保留 pending 和路径映射；不得有两个互相矛盾的当前入口。恢复前核对相关文件变化，只补未完成项，不阻塞无关工作。

## 7. 验收与重复执行

运行 `python .creator/scripts/check_docs.py --root . --require-complete`：检查登记状态、schema、入口、映射目标、未决项、Markdown 文件链接及目录边界。工具不验证锚点语义、产品决策正确性或原文完整性，不能单凭退出码宣称实质迁移完成。

- 关键原文逐项有去向；拆分前后任务、ID、验收和证据可追溯，链接更新或保留导航。
- 预期和现状不混写；旧条款不再冒充当前限制；未知与例外如实保留。
- 新会话从入口和相关计划能找到当前情况、任务/依赖、有效约束和验证入口。
- 重复执行不新增相同手册、不重编号、不重复归档或重放已解决冲突；无实质变化不刷新文件制造 diff。
- 全部迁移范围验证完才标 complete；pending 非空或映射仍有待处理不能标完成。已安装但 docs 未完成分别报告。

交付复用已有迁移记录，仅保留必要映射、未决项和证据。业务修复、生产迁移、发布、重审或兄弟仓同步需另有范围授权。
